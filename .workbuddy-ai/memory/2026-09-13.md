## Запуск приложения (важно для Windows-окружения агента)
- **`cmd.exe` заблокирован** и из Bash, и из PowerShell-инструмента, поэтому
  `Harness_Browser.bat` напрямую не запускается. Обходной путь — выполнить то,
  что делает ветка `:launch` батника: запустить
  `node_modules/electron/dist/electron.exe electron/main.js`.
- **GPU в песочнице не поднимается**: `main.js` форсирует
  `--ignore-gpu-blocklist --enable-gpu-rasterization`, Chromium падает с
  `FATAL ... GPU process isn't usable. Goodbye.` Лечится флагами
  **перед** путём к скрипту: `electron.exe --in-process-gpu --disable-gpu-sandbox electron/main.js`.
  (`--disable-gpu` не помогает — Chromium всё равно поднимает GPU-процесс.)
- Процесс, запущенный через `Start-Process` (PowerShell), песочница снимает по
  завершении команды; чтобы окно жило, запускать фоновой задачей Bash.
- Окно стартует на `electron/port-selector.html` и **ждёт клика
  «Запустить Harness»** — бэкенд спавнится только по IPC `start-harness`.
- Проверка, что новая тема реально отдаётся: `node apps/cli/lib/bin.js web --port 3000 --no-open`
  печатает `dsh web: http://127.0.0.1:3000/?token=...`; URL с токеном отдаёт
  редирект 303 с cookie, а `/plugins/??@deepseek-ai/dsh-client-ui-theme/client.js,...`
  (объединённый URL из `href` в index, `&amp;` → `&`) содержит новые токены.

## Самовосстановление Electron при недоступном GPU

Раньше `electron/main.js` безусловно включал `--ignore-gpu-blocklist` +
`--enable-gpu-rasterization`; на хосте без GPU Chromium не откатывается на софт,
а убивает весь процесс (`GPU process isn't usable. Goodbye.`) ещё до появления окна.

### Изменения
- `electron/main.js`:
  - определение режима: аргумент `--dsh-software-rendering[=reason]` **или**
    `DSH_SOFTWARE_RENDERING=1` → `softwareRenderingReason` = `'flag' | 'env' | 'crash'`;
  - в софт-режиме вместо акселерации ставятся `--in-process-gpu` +
    `--disable-gpu-sandbox` (единственная комбинация, которая выживает без GPU);
  - `app.on('child-process-gone')` ловит первое падение GPU-процесса и делает
    **одноразовый** `app.relaunch({args:[...process.argv.slice(1), '--dsh-software-rendering=crash']})`
    + `app.exit(0)`;
  - причина передаётся в страницу как query-параметр:
    `mainWindow.loadFile(path.join(__dirname,'port-selector.html'), softwareRendering ? {query:{gpu:reason}} : undefined)`.
- `electron/port-selector.html`: элемент `#gpuNotice` (`.status.hidden`) перед
  кнопкой запуска + синхронный `showGpuNotice()`, читающий
  `new URLSearchParams(location.search).get('gpu')`; текст разный для `crash` и для
  `flag|env`. Без параметра уведомление остаётся скрытым.
- `electron/preload.js` — **без изменений** (промежуточный IPC `gpu-mode`
  добавлен и откачен в пользу query-параметра: причина известна до создания окна,
  а синхронное чтение не гоняется с первой отрисовкой).

### Почему латч обязателен
`app.exit(0)` асинхронный, а Chromium переспавнивает GPU-процесс ~4 раза прежде чем
сдаться → без `gpuRelaunchIssued` обработчик плодил по инстансу на каждое падение
(наблюдал 4 строки «перезапуск» с одного запуска). С латчем — ровно 1.

### Тест
`electron/tests/port-selector-gpu-notice.test.js` (node:test + jsdom@29.1.1):
поднимает **настоящий** `port-selector.html` через `JSDOM(html, {url, runScripts:'dangerously', beforeParse(w){w.harnessAPI=stub}})`,
заглушка `window.harnessAPI` покрывает все методы, ошибки инлайн-скрипта собираются
через `VirtualConsole.on('jsdomError')` и валят тест. 3 кейса: без `?gpu` (скрыто),
`?gpu=crash` (текст про перезапуск), `?gpu=flag|env` (текст про `DSH_SOFTWARE_RENDERING`).
Мутационная проверка (удаление `showGpuNotice()` из копии в памяти) подтвердила,
что тест действительно падает. `pnpm run test:launcher` → 18/18.
**Важно:** `electron/` — CommonJS (`electron/package.json` `"type":"commonjs"`),
хотя корень — ESM; тесты в `electron/tests/*.test.js` пишутся через `require`.

### Проверка запуска
- Без флагов: в логе ровно одна строка «GPU-процесс упал (killed) — перезапуск в
  программном режиме», затем процесс завершается. **Перезапущенный инстанс

- С `--dsh-software-rendering=crash`: окно живёт, в логе только сообщение о софт-режиме

- `tasklist` в Git Bash отдаёт UTF-16 → grep считает поток бинарным, нужен `grep -a`.

## НАСТОЯЩАЯ причина «батник не запускается»: переводы строк LF вместо CRLF

Пользователь сообщил, что батник **в самом `testmodhas`** не запускается.
Мой предыдущий вывод «батник рабочий» был **ошибочным**: я проверял
эквивалентную команду через bash, а bash нечувствителен к переводам строк.

### Диагноз
`Harness_Browser.bat` был записан с окончаниями строк **LF** (`0a`), без `0d`:
```
40 65 63 68 6f 20 6f 66 66 0a   →   "@echo off\n"   (нужно 0d 0a)
CR = 0, LF = 31
```
`cmd.exe` требует **CRLF**. При LF-окончаниях не работает поиск меток, поэтому
`goto :install` / `goto :launch` (первые же исполняемые строки файла) не находят
цель → cmd печатает ошибку и **завершается, ничего не запустив**. Ровно симптом
пользователя.

### Ловушка в диагностике (не повторять!)
Проверка `grep -c $'\r' file` в Git Bash **врёт** — вернула 31 для всех файлов,
хотя CR было 0. Достоверный способ — считать байты:
`tr -cd '\r' < file | wc -c` и `tr -cd '\n' < file | wc -c` (или `od -An -tx1`).

### Масштаб
Сломаны **все 6** копий `Harness_Browser.bat` (CR=0, LF=31):
`testmodhas`, `testmodhas Final Build`, `hards Absolution`,
`horness Absolution Backup`, `testmodhasback app`, `testmodhas — копия`.
Исправен только `deepseek-harness/Harness_Browser.bat` (CR=53, LF=53) — самая
старая копия, от 03.09. То есть CR теряются при копировании/пересоздании.

### Исправление
`testmodhas/Harness_Browser.bat` переведён в CRLF:
`node -e "…readFileSync…replace(/\r?\n/g,'\r\n')…writeFileSync"`.
Копия оригинала — `.artifacts/Harness_Browser.bat.backup`.
Проверено: CR=31, LF=31 (было 956 байт → стало 987, ровно +31);
`diff` без учёта `\r` — **пусто**, логика не тронута; все метки `goto`
(`:install`, `:launch`) на месте; файл чисто ASCII.

**Проверить сам батник запуском не могу** — `cmd.exe` заблокирован и в Bash,
и в PowerShell. Обходить блокировку через `spawn('cmd.exe')` из Node не стал:
это обход защитного контроля.

## ГЛАВНАЯ причина «батник не запускается»: single-instance lock + мои же запущенные окна

После CRLF-фикса пользователь сообщил «не работает», симптом — **«чёрное окно
мигает и пропадает»**. То есть `cmd.exe` батник ИСПОЛНЯЕТ, и окно консоли
появляется, но окно приложения не открывается.

### Причина
`electron/main.js:651-663`:
```js
const gotLock = app.requestSingleInstanceLock();
if (!gotLock) {
  app.quit();                 // мгновенный выход: без окна и без сообщений
} else {
  app.on('second-instance', () => { /* фокус на существующем окне */ });
  app.whenReady().then(createMainWindow);
}
```
Пока ЖИВ хотя бы один экземпляр приложения, любой новый запуск не получает
блокировку и **молча завершается**. Я сам оставлял свои тестовые экземпляры
работающими (фоновые задачи `fBW7yU`, `hJRnCs`, `wVRzgj`) — и каждый запуск
пользователя умирал об этот лок. Симптом «мигает и пропадает» объясняется
полностью.

### Исправление
Убиты все экземпляры: `electron.exe` = 0, `DeepSeek Harness.exe` = 0,
блокировка свободна. Пользователю предложено запустить снова.

### УРОК (обязательно к соблюдению впредь)
**Никогда не просить пользователя запустить приложение, пока запущен мой
тестовый экземпляр.** Перед любой такой просьбой — останавливать свои фоновые
задачи и проверять `tasklist | grep -a electron.exe` = 0. Иначе любые попытки

## ГЛАВНАЯ НАХОДКА: встроенное распознавание речи в Chromium — серверное (06:46–06:53)

Довёл до конца единственный оставшийся открытый риск — и он оказался важным.

### Попытки проверить в рантайме (все провалились, 5 попыток)
Автономная проба Electron (`BrowserWindow` + `executeJavaScript`) не грузит
страницы: `ERR_FAILED (-2)` даже для `about:blank`. Что перепробовал:
1. `--in-process-gpu --disable-gpu-sandbox` (гипотеза «падает GPU») — не помогло.
2. `--no-sandbox`-подобные и отсутствие GPU-флагов — не помогло.
3. `loadFile` реального HTML / `data:` URL / `about:blank` — всё `ERR_FAILED`.
4. **Нашёл причину зависания проб:** `electron/main.js:75-76` ставит
   `disable-renderer-backgrounding` и `disable-background-timer-throttling` —
   без них рендерер скрытого окна троттлится и `executeJavaScript` не резолвится.
   Добавил их → проба стала корректно сообщать об ошибке вместо зависания.
   Но сама навигация всё равно падает.
5. Вывод: **рендерер не стартует в песочнице моего шелла**, при этом настоящее
   приложение страницы грузит нормально (заголовок окна «DSH локальная сборка» =
   это уже загруженный веб-UI Harness, т.е. file:// и http://localhost работают).
   Значит проба — тупик по среде, а не сигнал о поддержке речи.

### Ответ найден по документации (подтверждено несколькими источниками, 2025)
**Web Speech API в Chromium не является локальным** — распознавание выполняется
**на сервере Google**. Chrome везёт с собой нужные ключи; **Electron — нет**,
поэтому в Electron `start()` всегда даёт `network error` (проверяется и в dev, и
в упакованном .exe). Рекомендуемые сообществом альтернативы — локальные модели
(Whisper) или свой сервер, то есть настоящего «без API» распознавания в Electron нет.

writer lock». Код atomic-write это фиксирует прямо: «The contender never
removes an existing lock ... orphan recovery is an operator action».

**Практический вывод (важно!):** та же причина породила и пустые заглушки в
`node_modules` (массовые удаления при `pnpm install` блокировались). Симптомы
одной природы: «батник мигает», «Backend failed to start in time», пустые
папки вместо симлинков. Профилактика — запускать `dsh` и `pnpm install` в
**начале** хода, не смешивая с десятками других операций.

function thresholdPercent(threshold: number): string {

}

0.02→2%, 0.2→20%. Целые печатаются без «.0».
