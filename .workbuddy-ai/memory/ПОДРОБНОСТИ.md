### Контрастные темы (`ui-theme/src/styles/a11y.css`)
Устроены как **переопределение «алиасных» токенов** поверх обычной палитры
(`design-platform.css`). Три темы: `bw` (чёрно-белая), `yellow` (жёлтый на чёрном),
`daltonism` (для дальтонизма).
- **`bw` честно следует схеме**: два варианта — `body:not([data-ds-dark-theme])` и
  `body[data-ds-dark-theme]`. Поэтому непереопределённые токены берут правильное
  значение из базовой палитры.
- **`yellow` принудительно включает чёрную схему** (`color-scheme: dark` на `:root`),
  но применяется при **любой** основной теме. Значит он **обязан сам нести всю тёмную
  палитру**: иначе непереопределённые токены остаются светлыми (белые кнопки, поля,
  полосы прокрутки, блоки кода, подсветка наведения).
- **Урок 14.09.2026:** было 29 из 75 токенов → 46 белых пятен. Исправлено, покрытие
  **71/71 схемозависимых**. `color-scheme: dark` влияет только на системные элементы
  браузера, а не на цвета интерфейса — одного его мало.
- **Сторож:** `ui-theme/tests/a11y-styles.client.spec.ts` проверяет, что `yellow`
  переопределяет каждый токен, различающийся между светлой и тёмной палитрами
  (`--dsw-static-*` исключены — это палитра, а не алиасы).
- **Как проверить сторожа:** вырезать правку из копии текста файла и прогнать ту же
  логику — рабочий файл не трогать.
- **Симптом в интерфейсе:** белые пятна видны только при **светлой** основной теме.
  Если поставить «Тёмную», тёмные значения придут сами и ошибка спрячется.
- Палитра повторяет объявления дважды (два блока `body` и два `body[data-ds-dark-theme]`) —
  при разборе файла нужно собирать все вхождения, а не первое.

### КРИТИЧНО: «локальное» распознавание речи в Chromium — НЕ локальное
`SpeechRecognition` в Chromium ходит в **серверный** движок Google. Chrome везёт свои ключи,
**Electron — нет**: `start()` всегда `network`/`service-not-allowed`, хотя конструктор есть.
Диктовка и голосовой режим без API работают **только в обычном браузере** (Chrome/Edge, `dsh web`).
TTS (`speechSynthesis`) и захват экрана — действительно локальные, работают везде.
**«Модель смотрит живое видео» без API невозможно** — у модели нет видеовхода: захват настоящий и живой
(`getDisplayMedia`), кадры уходят либо в диалог, либо во внешний vision-сервис
(`/api/media/screen/analyze`). Рантайм-проверка невозможна (Electron в песочнице не грузит страницы).

## ⛔ Ошибка через мост Electron — НЕ `instanceof Error` (найдено 14.09.2026)
Отказ IPC приходит в страницу **чужим объектом**: `error instanceof Error` даёт
`false`, `String(error)` печатает `[object Object]`, а на экран уезжает сырое
`Error invoking remote method 'v2ray-start': Error: …`. Лечится так:
1. причину доставать **по свойству**, с проверкой формы:
   `typeof error === 'object' && typeof error.message === 'string'`;
2. срезать обёртку **одним закреплённым** выражением (Electron заворачивает дважды):
   `/^(?:[A-Za-z]*Error:\s*)?(?:Error invoking remote method '[^']*':\s*)?(?:[A-Za-z]*Error:\s*)?/`;
3. если после срезки пусто — вернуть исходный текст, а не пустоту.
Реализации-близнецы: `ui-settings-network/src/client/v2ray-bridge.ts`
(`bridgeErrorMessage`) и `electron/port-selector.html` (`readableError`).
⚠️ `oxlint` правило `no-base-to-string` **запретит** `String(error)` для постороннего
объекта — это не помеха, а подсказка: случай не разобран.
⚠️ Тест, бросающий ошибку из другого окружения jsdom, воспроизводит ровно эту
ловушку. Проверка `error instanceof Error` в тесте пройдёт, а в жизни — нет.

### ⛔ Главная грабля: файл состоит из МНОГИХ zstd-кадров
`zlib.zstdDecompressSync(весь файл)` **молча возвращает только ПЕРВЫЙ кадр**. Первый
кадр — это заголовок `session` (≈200 байт). Из-за этого сессия на 688 событий выглядит
как «1 событие, в чат не писали». **Так я уже один раз ошибся 14.09.2026** и сделал
неверный вывод «пользователь ни разу не отправлял сообщение».
Правильно: файл — это склейка кадров, по одному на событие (≈348 кадров на 198 КБ).
Разбирать по границам вручную: собрать все позиции магического числа `28 B5 2F FD`,
затем от текущей позиции пробовать распаковать срез до ближайшей следующей границы,
первый успех — конец кадра, продолжать от него. Готовый скрипт-разборщик писался
в `%TEMP%\read-session.mjs` / `filter-session.mjs` (можно пересоздать по этому описанию;
удобно вторым аргументом передавать список интересующих типов событий).

## Проверка, какой интерфейс реально отдаётся приложению
Адрес клиентского бандла лежит в графе `__DSH_BOOT__` **внутри HTML корневой страницы**:
`/plugins/??@deepseek-ai/dsh-client-<пакет>/client.js&rev=<отпечаток>`.
⚠️ Корневая страница отдаётся **только после входа**: `GET /?token=…` отвечает `303`
и **пустым телом**; затем нужен ещё один `GET /` с полученной cookie. Раздача идёт с
`cache-control: immutable`, но `rev` меняется при пересборке → кэш браузера не помешает.

**Быстрая проверка, что новый пакет вообще попал в приложение** (сделано 14.09.2026):
в HTML есть две ссылки `/plugins/??…` — одна из них перечисляет **все** клиентские
пакеты через запятую, и рядом лежит `__DSH_BOOT__` с записями вида
`{"id":"@deepseek-ai/dsh-client-ui-settings-network","url":"/plugins/??…","rev":"…","inject":[…]}`.
Достаточно найти имя пакета в HTML (5 упоминаний — норма: список, граф, порядок).
Затем запросить его URL с cookie → ожидается `200` и непустое тело.
**Обязательно контроль:** тот же путь с выдуманным именем пакета должен дать `404` —
иначе «200» ничего не доказывает.
Проверено: наш раздел отдался `200`, **27 785 байт**, внутри `settings.section`,
`order: 28`, `settings.network`, вшитые стили (`dsw-specific-input-major`),
`v2rayStatus` и `v2rayImportLink`; выдуманный пакет → `404`.
⚠️ Русские подписи искать по **фактическому** тексту из `locales.ts` (подпись раздела —
`Сеть`, а не «Настройки сети»): поиск по придуманной строке даёт ложное «нет».

## ⭐ Сквозная проверка серверной команды БЕЗ окна и браузера
Самый быстрый способ убедиться, что команда жива и что она отвечает (проверено 14.09.2026):
1. `node apps/cli/lib/bin.js web --port <свободный> --no-open` — в фоне; первая
   строка вывода: `dsh web: http://127.0.0.1:<port>/?token=…`.
2. `GET` по этому адресу с токеном → `303` + `set-cookie` = вход выполнен.
3. `POST http://127.0.0.1:<port>/api/<область>/<команда>`, заголовки
   `content-type: application/json` + `cookie`, тело:
   `{"type":"client-request","rpcId":"<uuid>","method":"<область>/<команда>","payload":{"args":{"request":{…}}}}`
4. Ответ: `{"type":"server-response","rpcId":…,"result":{"ok":true,"value":…}}`
   либо `{"ok":false,"error":{"code":…,"message":…,"details":{}}}`.

**Форма `payload` — только так:** `payload:{args:{request:{…}}}`. Имя `request` —
имя первого параметра метода; `signal` в теле не передаётся. Промежуточные
ошибки-подсказки: «must contain exactly one plain-object args field», затем
«args fields do not match the descriptor: missing "request"».
- Код протокола: `packages/client/connection/src/client/rpc.ts` (POST на
  `<origin><channel>/<endpoint>`), `api-path.ts` (префикс `/api`),
  `browser-auth.ts` (токен в адресе → cookie).
- **Только `node:http`, не `fetch`** — в песочнице HTTP_PROXY/HTTPS_PROXY уводят
  запросы к loopback через прокси.
- После проверки убедиться, что порт освободился (`netstat -ano | grep -a ":<port>"`).

**Корень жалобы «бесконечный цикл не удаляет» — два независимых дефекта:**
1. Атрибут `hidden` у кнопок этого окна **не работал**: `.hidden { display: none
   !important }` перебивал его, а сам атрибут — лишь догадка браузера. Кнопка
   считалась скрытой для кода, но оставалась на экране и **принимала нажатия**
   (нажатие выглядело как «ничего не произошло»).
2. Досрочный `return` при успехе пропускал возврат кнопок в рабочее состояние —
   в статусе «удалён», а кнопка всё ещё показывает занятость.

**Исправлено:** правило `.btn[hidden] { display: none; }`; пара кнопок больше
**не прячется вообще** (управляет только `disabled`); ни одна ветка не выходит
раньше отрисовки; состояние после действия берётся **из ответа**, а не из памяти
окна.

**Приборы, которыми это ловилось:**
- `MutationObserver` на атрибут — показывает, **писал ли код вообще**.
- `getComputedStyle(el).display` — показывает, **что реально с экрана**.
- В JSDOM `dispatchEvent(new MouseEvent('click'))` **доставляется и по
  `hidden`-элементам** — тест «нажмёт» кнопку, которой человек не видит.
  Поэтому тестам про видимость верить нельзя без проверки `display`.
- Пробники держать в `electron/tests/_*.mjs`: в корне `jsdom` не находится.

**Файл `electron/port-selector.html` — HTML с инлайновым JS, не модуль.**
Тесты берут его через JSDOM и подсовывают фальшивый `harnessAPI`. Новый вызов
оболочки обязан быть: 1) в `preload.js`, 2) в `handleChannels` в
`electron/tests/shell-security.test.js`, 3) заглушкой в `mount()` в
`port-selector-v2ray.test.js`.

## Команды сборки и проверки интерфейса (вынесено 18.09.2026)

Собирать напрямую, без `pnpm`:
- библиотеки клиента: `tsdown --env.DSH_BUILD_FACE client`;
- страница: `cd apps/web && mv dist dist-old && ../../node_modules/.bin/vite build --emptyOutDir && rm -rf dist-old`.
  **Почему не `--outDir`:** плагин `emit-preview-page` (`apps/web/vite.config.ts`)
  пишет `preview.html` жёстко в `dist/` — при другом каталоге страница
  собирается **без** него (128 файлов вместо 129).

**Как проверять «функция в интерфейсе»** — не `grep` по файлу плагина, а сервер:
запустить `dsh web`, взять токен, `curl --noproxy '*'` (в системе прокси
`127.0.0.1:50480`), сначала `?token=...` → 303 + cookie, потом `/`.
Запрашивать бандл надо **по `__DSH_BOOT__.entries[].url`** вместе с `&rev=`:
тот же путь без `rev` даёт 404. `/` без токена отвечает **401** — это норма.

**«Backend failed to start in time» — воспроизвести вручную:**
`rm -f ~/.dsh/.credentials.yaml.lock; node apps/cli/lib/bin.js web --port 18777 --no-open`.
Частая причина: **новый пакет хоста без `node_modules`** роняет всё дерево
(`Cannot find package '@deepseek-ai/cordis'`). `pnpm install` недоступен →
линки делать **junction**:
`New-Item -ItemType Junction -Path packages\<группа>\<пакет>\node_modules\@deepseek-ai\<имя> -Target <реальный путь>`.
`ln -sfn` на этой машине даёт **пустой каталог** → `TS2307`. Ориентир по
составу ссылок — рабочий сосед (`agent-default-model`).
